## 프로젝트 개요

**Order Purchase Automation**은 Slack 발주 요청과 발주 파일 감지를 시작점으로, 구매입력 데이터를 자동 정리하고 최종적으로 Ecount ERP 구매입력까지 연결하는 업무 자동화 프로젝트입니다.

전체 흐름은 크게 두 단계로 나뉩니다. 먼저 Slack에서 발주 요청을 받아 외부 발주 처리 서버를 호출하고, 생성된 통합 발주서를 Google Drive에 저장합니다. 이후 Drive 또는 Gmail에서 감지된 발주 파일을 파싱해 품목코드 매핑·배송비 계산·구매입력 시트 누적·ERP 등록까지 이어지는 반복 업무를 Google Apps Script 기반으로 자동화했습니다.

## 개발 배경

발주 업무는 단순해 보이지만 실제 운영에서는 예외가 많습니다.

- 업체마다 다른 엑셀 양식
- 카페24 품목명과 이카운트 품목명 간 불일치
- 옵션 상품, 추가 구매 상품, 사은품, 비고가 섞인 주문 행
- 무료배송, 합배송, 도서산간 추가요금 등 복잡한 배송비 규칙

또한 담당자의 업무가 발주와 구매입력만 있는 것은 아니기 때문에, 발주 후 바로 구매입력을 하지 못하고 정산 시점에 몰아서 처리하는 경우가 많았습니다.
그래서 이 프로젝트를 통해 발주서 수신부터 ERP 등록 직전까지의 흐름을 자동화하여 사람이 확인해야 하는 지점만 남기는 것을 목표로 만들었습니다.

## 핵심 기능

### Gmail 발주 메일 자동 감지

Gmail에서 특정 발신자와 제목 키워드에 해당하는 발주 메일을 주기적으로 감지합니다. 첨부된 `xlsx`, `xls`, `csv` 파일을 수집하고, 원본 파일은 Google Drive에 보관해 재처리와 이력 추적이 가능하도록 구성했습니다. 초기에는 매입 자동화를 먼저 구현했기 때문에, 업체에 발주 메일을 보낼 때 참조로 수신한 발주 파일을 Gmail에서 수집하는 방식으로 시작했습니다.

### Slack 기반 발주 요청 처리

Slack Slash Command와 Event payload를 Apps Script Web App이 수신합니다. 허용된 채널의 요청만 처리하고, 요청은 Script Properties 큐에 적재한 뒤 내부 발주 처리 서버 엔드포인트로 전달합니다.

워크플로우 기준으로는 Slack 요청이 GAS를 거쳐 서버로 전달되고, 서버는 카페24 주문 데이터를 조회해 통합 발주서를 생성한 뒤 Google Drive에 업로드합니다. 이후 회사별 발주서 분리 과정을 거쳐 매입 플로우의 입력 파일이 됩니다.

### Drive 발주 파일 감지

발주 자동화가 진행되면서 더 이상 참조 메일을 통해 파일을 수집할 필요가 없어졌습니다. 따라서 Google Drive 감지 폴더에 새로 생성된 발주 파일을 감지하고 조건에 맞는 파일을 파싱 파이프라인으로 넘깁니다.

### 업체별 발주서 파싱

발주서마다 헤더 위치와 컬럼명이 다르기 때문에 3단계 방식으로 헤더와 컬럼을 감지합니다.

1. 업체별 발주양식 설정값과 키워드 정확 매칭
2. 바이그램 유사도 기반 보정
3. OpenAI API 기반 LLM 판단

이를 통해 `품목명`, `수량`, `전표일자`, `옵션`, `배송지주소` 등 구매입력에 필요한 값을 발주서에서 추출합니다.

### 옵션 및 추가상품 분해

커머스 발주서에는 한 행 안에 본품, 옵션, 추가상품이 함께 들어오는 경우가 많습니다. 이 프로젝트는 `키=값` 형태의 옵션 문자열을 분석해 본품과 추가상품을 별도 행으로 분리합니다.

예를 들어 본품은 배송비 계산 대상에 포함하고, 추가 옵션 상품은 품목코드와 단가는 매핑하되 배송비는 본품에 포함된 것으로 처리합니다. `선택안함`, `사은품`, `메모`, `비고`처럼 구매입력 대상이 아닌 값은 제외합니다.

### 품목코드 자동 매핑

Ecount 품목 데이터를 기준으로 품목매핑 시트를 동기화하고, 발주서의 품목명과 실제 Ecount 품목코드를 연결합니다.

동일 거래처의 품목 목록을 기준으로 후보를 제한하고, 발주 품목명을 중복 제거한 뒤 배치 단위로 LLM 매칭을 수행합니다. LLM이 반환한 코드가 실제 품목매핑 목록에 존재하는지 검증해 환각으로 인한 잘못된 코드 입력을 방지했습니다.

### 배송비 자동 계산

배송비는 품목 단위의 단순 금액이 아니라 주문 조건에 따라 달라집니다. 이 프로젝트는 다음 규칙을 순서대로 적용합니다.

- 배송비 0원 품목 무료배송 처리
- 무료배송 기준금액 충족 여부 확인
- 합배송 불가 품목 개별 배송비 계산
- 합배송 가능 수량 기준 배송 횟수 계산
- 도서산간 주소 키워드 기반 추가요금 행 생성

계산이 끝난 뒤 동일 품목코드는 수량 기준으로 병합하고, 도서산간 추가요금은 별도 품목 행으로 추가합니다.

### Google Sheets 기반 검수 화면

자동 처리 결과는 구매입력 스프레드시트에 누적됩니다.

- **이카운트 등록**: 파싱과 매핑이 완료된 메인 데이터
- **매입내역**: ERP 등록 완료 후 누적되는 입력 이력
- **파싱실패**: 파싱 실패, 데이터 없음, 미매핑 항목 관리
- **업체별 조회 시트**: 전체 등록 시트를 업체별로 나눠 보는 읽기 전용 뷰

담당자는 시트에서 상태를 확인하고, 체크박스 또는 일괄 실행으로 Ecount 등록을 진행할 수 있습니다.

### Ecount ERP 구매입력 등록

검수가 끝난 데이터는 Ecount `SavePurchases` API를 통해 구매입력으로 등록됩니다. 등록 성공 시 상태와 등록일시를 기록하고, 실패한 행은 오류 상태로 남겨 담당자가 원인을 확인할 수 있게 했습니다.

### Slack 알림

`purchase` 앱은 파싱 실패, 미매핑, 처리 완료 같은 운영 이벤트를 Slack으로 전달합니다. 담당자는 시트에 들어가기 전에도 어떤 파일에서 문제가 발생했는지 확인할 수 있습니다.

## 아키텍처

![Order Purchase Automation 워크플로우](/images/projects/order-purchase-automation/order-purchase-automation_workflow.svg)

프로젝트는 크게 발주 플로우와 매입 플로우로 구성되며, 저장소 안에서는 `purchase`와 `ordering` 두 Apps Script 앱이 이 흐름을 담당합니다.

- **purchase** — Gmail 발주 메일 감지, 엑셀 파싱, 품목 매핑, 배송비 계산, Google Sheets 누적, Ecount 구매입력 등록
- **ordering** — Slack Slash Command/Event 수신, 요청 큐 적재, 내부 발주 처리 엔드포인트 호출

워크플로우 상단의 발주 플로우에서는 Slack 요청이 GAS와 외부 발주 처리 서버를 거쳐 통합 발주서를 만들고, Google Drive에 저장합니다. 이후 회사별 발주서가 생성되면 하단의 매입 플로우가 시작됩니다.

매입 플로우의 중심은 `purchase` 앱입니다. Gmail과 Drive에서 원본을 가져오고, 설정 스프레드시트의 업체 규칙과 Ecount 품목매핑 데이터를 활용해 구매입력 데이터를 만듭니다. 이후 담당자가 Google Sheets에서 확인한 뒤 Ecount API로 등록합니다.

## 주요 구현 포인트

### 자동화와 수동 검수의 경계 설정

ERP 등록까지 완전 자동으로 밀어 넣기보다, Google Sheets에 `대기`, `미매핑`, `완료`, `실패` 상태를 남기고 담당자가 최종 확인할 수 있도록 설계했습니다. 업무 자동화에서 중요한 것은 모든 판단을 기계에 맡기는 것이 아니라, 사람이 봐야 하는 예외를 빠르게 드러내는 것이라고 생각했습니다.

### 실패 항목 재처리 흐름

파싱 실패나 미매핑 항목은 별도의 `파싱실패` 시트에 기록됩니다. 원본 파일을 보관하고 있기 때문에 파일 단위 재파싱이 가능하고, 매핑을 보정한 개별 품목 행은 체크박스로 다시 이카운트 등록 시트로 이동할 수 있습니다.

### 품목 매칭의 환각 방어

LLM은 품목명 해석에는 유용하지만 없는 품목코드를 만들어낼 위험이 있습니다. 그래서 LLM 결과를 그대로 신뢰하지 않고, 반드시 해당 거래처의 품목매핑 목록에 존재하는 코드인지 검증한 뒤에만 확정합니다.

### 배송비 계산의 데이터화

무료배송, 합배송, 도서산간 규칙을 코드에서만 동작하는 것이 아니라 설정 시트에서 관리할 수 있습니다. 담당자가 기준금액이나 합배송 가능 수량을 수정하면 다음 발주 처리부터 계산 규칙에 반영됩니다.

## 프로젝트를 통해 얻은 점

이 프로젝트를 진행하면서 느낀 점은, 업무 자동화의 목표가 단순히 "사람이 하던 일을 AI나 코드로 대체하는 것"에 있지 않다는 점이었습니다. 더 중요한 것은 **실무 담당자가 반복 업무에서 벗어나 더 적은 확인 작업으로 같은 업무를 처리할 수 있도록 만드는 것**이었습니다.

기존에는 카페24에서 업체별 주문을 확인하고, 주문 내역을 내려받고, 업체에 발주 파일을 보낸 뒤, 다시 ERP 구매입력까지 연결하는 작업이 반복적으로 발생했습니다. 특히 발주 후 바로 구매입력을 하지 못하면 정산 시점에 여러 발주 건을 한 번에 입력해야 했고, 이 과정에서 담당자의 시간이 많이 소모되었습니다.

또한 발주와 구매입력은 비용에 직접 연결되는 업무이기 때문에, 단순히 빠르게 처리하는 것만으로는 충분하지 않았습니다. 잘못된 품목이나 수량, 배송비가 ERP에 등록되면 실제 손실로 이어질 수 있는 민감한 영역이었습니다.

그래서 이 프로젝트에서는 "완전 자동화"보다 **담당자가 직접 판단해야 하는 지점과 시스템이 대신 처리할 수 있는 지점을 나누는 것**에 집중했습니다. 발주서 수집, 파싱, 품목 매핑, 배송비 계산, 구매입력 시트 누적처럼 반복적이고 규칙화할 수 있는 부분은 자동화하고, 미매핑 품목이나 파싱 실패처럼 사람이 확인해야 하는 예외는 별도로 드러나게 만들었습니다.

이를 통해 담당자는 모든 발주 데이터를 처음부터 입력하는 대신, 자동으로 정리된 구매입력 데이터를 검수하고 예외 항목만 보정하는 방식으로 업무를 처리할 수 있게 됐습니다. 단순히 입력 시간을 줄이는 것을 넘어, 어디서 문제가 발생했는지 확인하고 다시 처리할 수 있는 흐름이 생긴 점이 의미 있었습니다.

다만 자동화를 만들었다고 해서 바로 의미 있는 개선이 되는 것은 아니었습니다. 자동화를 처음 도입했을 때는 담당자가 기존과 다른 작업 방식에 어색함을 느끼는 부분도 있었습니다. 실제 담당자가 자동화된 흐름을 사용하지 않거나 기존 방식보다 더 불편하게 느낀다면, 자동화는 업무 개선으로 이어질 수 없습니다.

그래서 기능을 구현한 뒤에는 담당자에게 사용 방법을 충분히 설명하고, 실제 업무에서 계속 사용할 수 있는지 확인하는 과정이 필요했습니다. 어느 지점에서 불편함을 느끼는지, 반복 업무가 실질적으로 줄어들었는지 확인하면서 개선해 나가야 자동화가 의미 있는 업무 개선으로 이어질 수 있다고 느꼈습니다.

이 프로젝트를 통해 배운 점은 자동화의 가치는 구현 자체가 아니라 실제 업무에서 사용되는 방식으로 판단해야 한다는 것입니다. 담당자가 반복 업무에서 벗어나 더 적은 확인 작업으로 같은 업무를 처리할 수 있고, 사용 과정에서 발견된 불편함을 계속 개선할 수 있을 때 자동화가 실질적인 업무 개선으로 이어진다고 생각합니다.
